## 结论概览

未发现 P0。P1 三条同源：**前端把"只读探测命令"当写命令提交**，导致 DNS 能力判定在真实设备上大概率失败，并把"未判定"当成"可用"。其余为契约字段缺失、陈旧/错误状态呈现与少量边界问题。整体工程质量偏高（代际校验、双重并发守卫、严格的响应字段校验在多数页面已做到），下面只列有实际机理的缺陷。

| 级别 | 数量 | 主题 |
| --- | --- | --- |
| P0 | 0 | — |
| P1 | 3 | 只读探测走写通道、探测超时→全局锁写、能力未知被当作可用 |
| P2 | 6 | keyExpiry 误报、dns 降级分支缺字段、探针错误被覆盖、无效响应不清列表、timedOut 死代码、保存静默失败 |

## P1

#### [P1] 只读探测命令（dns-probe / coexist-info / coexist-check / diag-check / socks-check）被前端当写命令提交，受写权限门禁与单写槽排他限制

- 位置：`webui/src/api.ts:46-51`（读命令白名单）与 `webui/src/api.ts:63-72`

```ts
const READ_COMMANDS = [
  'backend-info', 'owner-capability', 'hooks-get', 'status', 'exit-routing',
  'peers', 'exitnodes', 'tun', 'dns', 'accounts', 'serve-list', 'funnel-list',
  'traffic', 'traffic-uids', 'apps', 'routes-get', 'subnet-routes-get',
  'settings-get', 'context-get', 'context-status', 'logs', 'compat', 'files-inbox',
  'taildrop-targets', 'file-send-status', 'file-send-history', 'backup-list',
  'restore-preview', 'trial-status',
];
```
```ts
const request = command === 'login'
  ? startNative('app.login', ...)
  : startNative(read ? 'control.query' : 'control.mutate', { command, arguments: args.map(String) });
```

- 问题机理：`dns-probe` 不在 `READ_COMMANDS`，因此 `read=false` → 走 `control.mutate` → `ControlClient.submit()`。而原生侧明确把它归为只读：

  - `android/app/src/main/java/dev/foxderin/tail/ControlClient.java:72-77`
    ```java
    static boolean readOnlyOperation(String command) {
        switch (command) {
            case "peer-ping": case "speedtest-exitnodes": case "derp-speedtest":
            case "coexist-info": case "coexist-check": case "diag-check": case "socks-check": case "dns-probe": return true;
    ```
  - `ControlClient.java:186-189` 的 `submit()` 对**所有**走 mutate 的命令施加写门禁与排他：
    ```java
    if (!(stop ? canStop() : canWrite())) { reject(terminal, ...control_unavailable); ... return; }
    if (busy()) { reject(terminal, context.getString(R.string.control_busy, label)); return; }
    ```
    其中 `canWrite() = compatible && !upgrading && commands.contains("exit-routing") && commands.contains("context-status")`（`ControlClient.java:79`），`busy() = id != null || submitting`。

- 触发条件（两条都常见）：
  1. **升级中/后端命令集降级**：只要后端不暴露 `exit-routing` 或 `context-status`，`canWrite()=false`，探测必然 `control_unavailable`。
  2. **并发写**：用户点保存 → `settings-set` 在途 → 进入设置页（或 `SettingsMaintenance` 展开诊断）触发探测 → `control_busy`。`ControlClient.submit` 无排队，直接拒绝。
  同类还有 `coexist-info/coexist-check`（`pages/Coexistence.tsx:86,104`）、`diag-check`（`pages/Diag.tsx:78`）、`socks-check`（`pages/Tunnel.tsx:89`）、`peer-ping/speedtest-exitnodes/derp-speedtest`。`pages/Coexistence.tsx:41` 已经把 `!nativeControl().canWrite` 写进自己的 `busy()`，等于在 UI 层绕这个不一致，进一步说明契约本身错位。

- 用户可见影响：
  - 设置页 DNS 模式的能力判定拿不到结论（见 P1 第三条）；共存检测在写操作进行时直接报错；诊断/隧道自检偶发失败。
  - 探测期间 `nativeControl().busy` 为真 → 全局 `locked()` 生效（`Settings.tsx`、`ServiceControls`、`Files.tsx:34`），并且 `pages/tools-refresh.ts:26` 的 `available()` 含 `!nativeControl().ownsMutation`，此时所有页面读刷新被抑制。
  - `ControlClient.rememberTask()` 会把探测登记为任务，`AppShell.tsx:147-156` 顶部横幅会显示"任务运行中"，属噪声。

- 证据：已实证（读码闭环：`api.ts` 白名单 → `submit()` 门禁 → `readOnlyOperation` 名单三处对不上；命令本体在 `foxytail.webapi.sh:68,96` 与 `foxytail.webapi-network.sh:263` 均在普通命令分派表内，不受 mutate 路径限制）。

- 修复建议：
  1. 把只读探测命令加入 `READ_COMMANDS`（`control.query` 路径没有 `canWrite()`/`busy()` 门禁，且有 `WebBridge.query()` 的 `observationRevision:accountRevision:wire` 去重），或新增独立的 `control.probe` 通道。
  2. 若保持 mutate 路径，则在 `ControlClient.submit()` 中把门禁改为 `if (!(stop ? canStop() : readOnlyOperation(args[0]) || canWrite()))`，并在 `busy()` 时对只读命令改为排队而非拒绝。
  3. 让 `readOnlyOperation()` 与前端 `READ_COMMANDS` 同源（例如由 `commands` 快照携带 `readOnly` 标记），避免两份名单继续漂移。

#### [P1] 探测类命令最长 40s，超过原生 30s 传输超时 → 进入 unknown 状态并全局锁写

- 位置：`tailscale/scripts/foxytail.webapi-network.sh:265,275` 与 `android/app/src/main/java/dev/foxderin/tail/ControlClient.java:217`

```sh
_cdp_out=$(_op_exec 20 "${TS_SCRIPTS_DIR}/foxytail.dns" probe-transparent 2>&1)
...
_cdp_out=$(_op_exec 20 "${TS_SCRIPTS_DIR}/foxytail.dns" probe-hijack 2>&1)
```
```java
JSONObject response = RootApi.json(context, null, null, null, 30, new RootApi.Call(), wire);
```

- 问题机理：`cmd_dns_probe` 串行执行两次内核探测，每步 `_op_exec 20`（20s 预算），最坏 40s+；而 mutate 传输层固定 30s 超时。超时后 `submit()` 走 `markUnknown(e)`（`ControlClient.java:226-232` 附近）→ `unknown=true`、`id` 仍非空 → `busy()` 恒为 true。`coexist-info`（`foxytail.webapi-coexist.sh:51` `_op_exec 30` + `_coexist_snapshot` 的 `ts_cli 10`=最坏 40s 量级）同理。
- 触发条件：内核能力探测变慢的设备（低端机、模块加载慢、`iptables` 探测超时），或备份/恢复等长任务与探测重叠时。
- 用户可见影响：任务横幅"结果未确认，请勿重复提交"常驻；所有写操作（保存、启停、恢复）被禁用，直到用户手动按下 acknowledge（`AppShell.tsx:155-156` → `control.acknowledge`，`ControlClient.java:325-334`）。恢复路径存在，因此定为 P1 而非 P0，但普通用户不知道该按哪个按钮。
- 证据：已实证（超时值两处读码确认；`markUnknown` 分支未清 `id`，`busy()` 因此持续为真）。
- 修复建议：探测拆成两个独立命令（`dns-probe-transparent` / `dns-probe-hijack`）各自 `_op_exec` 一次；或把 `submit()` 的超时按命令配置（探测类 ≥ 2×步骤预算 + 余量）；`markUnknown` 对 `readOnlyOperation(command)` 直接清除 `id` 并保留结果未知标记，避免只读操作把全局写锁定。

#### [P1] DNS 能力"未知"被前端当作"可用"：探测失败时仍可保存 transparent / hijack 模式

- 位置：`webui/src/pages/Settings.tsx:97-113,118-121,181-186`

```ts
const probe = await scope.api('dns-probe');
if (probe.cancelled || disposed) return;
if (probe.ok) { setTransparentAvailable(probe.transparentAvailable === true); ... }
```
```ts
if (field.key === 'DNS_MODE' &&
    ((value === 'transparent' && transparentAvailable() === false) ||
     (value === 'hijack' && hijackAvailable() === false))) return;
```
```ts
if (choice.value === 'transparent' && transparentAvailable() === false) { ... disabled: true ... }
```

- 问题机理：能力三态 `true | false | null`，但所有守卫都只拦 `=== false`。P1 前两条一旦让探测失败（门禁拒绝 / 超时 / `dns` 降级分支缺字段），`transparentAvailable`/`hijackAvailable` 保持 `null`，界面既不置灰也不提示，`saveKey()` 直接放行。
- 触发条件：任何一次探测失败（见 P1 前两条）；或后端 `dns` 状态走了降级分支（见 P2「`cmd_dns` 降级分支缺字段」）——该分支下每次进设置页都会重新探测，探测失败即回到"未知=可用"。
- 用户可见影响：在无 `iptables REDIRECT`（transparent）或端口劫持不可用的设备上把 `DNS_MODE=transparent/hijack` 写入 `foxytail.conf`，重启后 MagicDNS 监听起不来（`foxytail.dns` 的启动拒绝行为属相邻模块，未深挖，但配置已落盘这一步是前端责任）。用户看到的是"设置保存成功"，之后 DNS 全挂。
- 证据：已实证（三态变量与三处 `=== false` 守卫）；后端是否启动即拒属待核实。
- 修复建议：区分三态——`null` 时禁用 `DNS_MODE` 选择并显示"能力未判定，请点此重试"（复用 `tools_dns_check` 文案），只有 `true` 才允许选；`saveKey()` 用 `!== true` 做 fail-closed 守卫；`loadTransparentCapability()` 失败时把 `probe.error` 落到该字段的 hint，而不是静默保留 `null`。

#### [P3] 文件名排序用 `localeCompare`，数字序列错序

(order() === 1 ? a.mtime - b.mtime : order() === 2 ? 0 : order() === 3 ? b.size - a.size : b.mtime - a.mtime) || a.name.localeCompare(b.name)

- 机理：无 `numeric: true`，`tailscale-10.log` 排在 `tailscale-9.log` 之前（`ft_name` 排序与同名时间戳并列时都受影响）。Taildrop 常见文件名正是带序号/日期的。
- 证据：已实证（标准 `localeCompare` 行为）。建议 `a.name.localeCompare(b.name, undefined, { numeric: true, sensitivity: 'base' })`。

#### [P3] `serveDeleteArgs` 抛异常但调用点未捕获

- 位置：`webui/src/serve.ts:50-55` 与 `webui/src/pages/Serve.tsx:81`
```ts
if (!mapping.canDelete) throw new Error('Unsupported Serve listener');
```
- 机理：`Serve.tsx` 的删除按钮若未按 `canDelete` 禁用（或后端出现 `proto === 'unknown'` 的监听器，`serve.ts:37` 会把 `canDelete` 置为 false），点击即抛出未捕获异常 → 无任何用户提示，控制台 unhandled rejection。
- 证据：待核实（未逐行确认按钮 disabled 表达式）。建议改为返回 `null` 并由调用点 `toastApiError`。

#### [P3] `createGuardedLoad` 在运行中丢弃显式刷新请求，`ErrorState.onRetry` 因此可能无效果

- 位置：`webui/src/pages/tools-refresh.ts:68-73`
```ts
return () => {
  if (disposed || running && !queueWhileRunning) return current;
  pending = true; blockedGeneration = -1; return start();
};
```
- 机理：`createGuardedLoad`（`queueWhileRunning=false`）在 `running` 时直接返回已存在的 `current`，既不排队也不新建；`SettingsBackup.tsx:132` 的 `onRetry={() => void load()}` 在上一次读未结束（例如刚被 `ownsMutation` 阻塞后重入）时会立刻 resolve，界面看起来"点了没反应"。
- 证据：已实证（分支语义）。建议 `running` 时至少 `pending = true`，与 `createQueuedRefresh` 的语义对齐，或让重试按钮同时显示 busy。

#### [P3] `resolverValid()` 未防护 `dns` 字段缺失

- 位置：`webui/src/pages/Coexistence.tsx:51`
```ts
const resolverValid = () => !resolverPort() || (portValid(resolverPort()) && Number(resolverPort()) !== info()?.dns.port);
```
- 机理：`info()?.dns.port` 只对 `info()` 做可选链；若 `info()` 非空但 `dns` 缺失（后端字段改名/降级），抛 `TypeError`。`detect()`（`:120`）确实校验了 `response.dns` 为对象，但 `info()` 也可能来自草稿恢复路径之外的其他写入点。
- 证据：待核实（当前仅 `detect()` 一个写入点，风险低）。建议 `info()?.dns?.port` 并保留 `undefined` 语义（不等于任何端口）。

## 功能闭环缺口

1. **`exitnodes` 读命令前端无任何调用点**（`webui/src` 中 0 处；`pages/ExitNodes.tsx` 只用 `status().peerList` + `speedtest-exitnodes`）。后端 `cmd_exitnodes`（`foxytail.webapi-network.sh:105`）与 `api.ts` 白名单都在，却没有入口，属"后端有、前端未接"。
2. **`traffic-uids` 读命令前端无调用点**（`pages/Traffic.tsx` 的 uid 视图直接取 `traffic summary` 的 `uids`）。两条路径并存，实际只走一条，另一条无从验证。
3. **`file-send-status` 前端无调用点**（发送进度改由 `files.snapshot` 推送），`READ_COMMANDS` 白名单里的这项在 UI 侧不可达。
4. **`backend-info` 前端无调用点**，仅原生 `ControlClient.java:132` 用于可用性检查——不属缺陷，但说明白名单与真实使用面已脱节（建议按"实际调用面"维护，而不是并列两份名单）。
5. **`cmd_dns` 降级分支缺 13 个契约字段**（见 P2）：前端有渲染位、后端不产出。
6. **后端错误文案未本地化**：所有 `jerr '...'` 文案（如 `an upgrade is in progress; retry after it completes`、`trial status failed or cancelled`、`settings-set: ...`）原样经 `error` 字段进入中文界面，`i18n` 无对应 key，`t()` 也无从翻译（`i18n.ts:323-325` 只查字典）。中文用户会看到英文错误串。
7. **`settings-set` 只写单键**（`foxytail.webapi-config.sh` 的 `cmd_settings_set`），前端"保存全部/重置"是按字段循环逐个提交，没有事务语义：中途失败会出现"部分字段已落盘、部分仍在草稿"的状态，界面靠 `restartRequired` 兜底，但用户不知道哪几个成功了。属设计取舍，记录在案。
