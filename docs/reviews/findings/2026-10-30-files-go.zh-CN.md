## 缺陷清单

#### [P1] 已导入回执成了永久墓碑：删掉收件箱里的文件后，同内容同名的重发会被静默吞掉，且 shared 源文件同时被删除

- 位置：`native/foxyfiles/taildrop.go:309`（回执命中即丢弃）+ `native/foxyfiles/taildrop.go:191`（无条件删源）

```go
// taildrop.go:309
if info, statErr := receipts.Lstat(receipt); statErr == nil {
    if !info.Mode().IsRegular() {
        return "", nil, errors.New("invalid Taildrop receipt")
    }
    return "", before, nil          // 已收过 -> 不导入，但调用方随后照样删源
}
```

```go
// taildrop.go:183
if published != "" {
    result.Files = append(result.Files, published)
    result.Received++
    importedBytes += before.Size()
    slots--
}
// The receipt, not the shared copy, is the dedupe record: once
// publication is durable the source only costs shared space.
if err := removeTaildropSource(incoming, name, before); err != nil {   // :191 无论是否真的导入都删源
    result.warn(...)
}
```

- 问题：回执 `sha256(name || 0x00 || sha256(content))` 是**永久**记录（`.taildrop` 目录只由 `Mkdir` 创建，`sweepAux`/`maintain`/脚本 `cmd_file_clear` 都不清理它，无过期逻辑）。回执命中时 `importTaildropFile` 返回 `("", before, nil)`，`importTaildrop` 不计数、不 `skip`、不 `fail`，紧接着仍调用 `removeTaildropSource` 把 `/sdcard/Download/Taildrop/<name>` 删掉。
- 触发条件：① 曾经成功接收过 `X`（回执落盘）；② 用户从 App 收件箱删除 `X`（`file-delete`）或“清空收件箱”（`cmd_file_clear` 显式保留 `.taildrop`，所以回执仍在）；③ 对端再次发送**同名同内容**的 `X`。这正是“上次传输失败/我删了想再要一份”的最常见路径。
- 影响：用户点“接收”后什么都没发生（`received:0`、`ok:true`），而 shared 里那份新落地的文件已经被删除。App 里没有该文件、Download/Taildrop 里也没有了，UI 零提示（见 P1 下一条）。真正可恢复的只剩上次导出留下的 `/sdcard/Download/X`，一旦用户当时改过名/移走即彻底丢失。
- 证据：**已实证**。PoC（`/tmp/ffaudit/zz_audit_test.go`，`go test -run TestAuditReceiptTombstone -v`）：

```
first:  {OK:true Received:1 Files:[a.txt] Ignored:0 Skipped:[] SkippedCount:0 Failed:[] FailedCount:0 Warnings:[]}
second: {OK:true Received:0 Files:[]    Ignored:0 Skipped:[] SkippedCount:0 Failed:[] FailedCount:0 Warnings:[]}
inbox a.txt after re-drop:  stat err = no such file or directory
shared source after re-drop: stat err = no such file or directory
```

（第二次调用同时没有 `skipped`/`failed`/`warnings`，调用方拿不到任何信号。）
- 修复建议：任选其一并落实
  1. 回执带“存活校验”：命中回执时先 `inbox.Lstat(name)`，只有当收件箱里那份仍在（或同 inode/同内容）才视为重复；否则删回执并正常导入。
  2. 回执加 `ImportedAt` 并设过期（例如 7 天），或让 `file-delete`/`file-clear` 同步删除对应回执（需要回执能反查文件名，当前 hash 不可反查，建议把回执内容写成包含 name/size/sum 的 JSON 而不是空文件）。
  3. 无论如何，**回执命中时不要删源**：`if published == "" { continue }` 放在 `removeTaildropSource` 之前，并 `result.warn(...)` 记录“已经收过、源文件保留”。

#### [P1] `receive` 的 `skipped`/`failed`/`warnings` 全链路被丢弃：收件箱满、单文件超限、导入中途失败时 UI 显示成功且零提示

```go

```

```sh
# foxytail.webapi-tools.sh:259
jqr -n -c --argjson count "${_fr_count}" --argjson exported "${_fr_exported}" --argjson ignored "${_fr_ignored}" \
  '{ok:true,received:$count,exported:$exported} + (if $ignored > 0 then {ignored:$ignored} else {} end)'
```

- 问题：Go 侧把“逐文件失败”从致命错误降级为 `Failed[]`/`Skipped[]` 并保持 `OK:true`（设计上合理：一个坏文件不该阻塞其余），但**消费端一个字段都没接**：`cmd_file_receive` 用一条严格 jq 断言通过后，只把 `received`/`exported`/`ignored` 重新拼装输出，`skipped`、`skippedCount`、`failed`、`failedCount`、`warnings` 全部丢失（全仓库 grep 零命中）；`Files.tsx:76` 也只有 `if (!result.ok && !result.cancelled) setNotice(...)`。
- 触发条件：收件箱文件数达到 10000（`inbox.go:14`）后继续丢文件；单文件 > 2 GiB；单次调用累计 > 4 GiB；源文件在导入过程中被改写（`shared file changed while importing`）；私有卷 ENOSPC；`.taildrop` 回执不可写等。
- 影响：用户点“接收”看到的是“成功”，但**每个文件都被跳过/失败**，收件箱毫无变化；或 5 个文件只进来 2 个而 UI 不提另外 3 个。更糟的是配合上一条（回执墓碑）时连 `skipped` 都没有，连日志都查不到原因。用户唯一能做的“再点一次接收”是幂等的失败，形成无解循环。
- 证据：**已实证**。PoC（`go test -run TestAuditInboxFullSilent -v`）：

```
full inbox result: {OK:true Received:0 Files:[] Ignored:0 Skipped:[{Name:b.bin Reason:private inbox is full} {Name:a.bin Reason:private inbox is full}] SkippedCount:2 Failed:[] FailedCount:0 Warnings:[]}
```

即该响应能完整通过 `foxytail.webapi-tools.sh:247` 的断言，被裁剪成 `{"ok":true,"received":0,"exported":0}` 返回给 App。
- 修复建议：
  1. `cmd_file_receive` 把 `skipped`/`failed`/`warnings` 原样透传（`+ (if (.skippedCount//0)>0 then {skipped,total:.skippedCount} else {} end)`，并同样透传 `failed`），断言里增加 `(.skippedCount//0)|type=="number"`。
  2. `Files.tsx` 在 `received==0` 且存在 `skippedCount+failedCount>0` 时显示 notice（复用 `ft_ignored` 的文案模式，新增 `ft_skipped`/`ft_failed`）。
  3. 全量失败（`Received==0 && (SkippedCount+FailedCount)>0`）时让 `receive` 走非零退出码，这样 `_op_exec 60 ... || jerr` 自然把原因带给 UI——但要注意此时 `ok` 语义与 shell 断言要保持一致。

#### [P2] `records()` 把任意 `load` 失败都改名 `.corrupt`：一次 EMFILE/EIO 就能让传输历史永久消失

- 位置：`native/foxyfiles/transfer_store.go:247-253`

```go
record, err := s.load(id)
if err != nil {
    // Quarantine instead of failing every query: a torn record must not
    // wedge history.
    s.root.Rename(entry.Name(), id+".corrupt")
    continue
}
```

- 问题：`load` 的失败原因被一视同仁地当成“记录损坏”，而它同时也会因 `open` 的系统错误失败（EMFILE：进程 fd 用尽；EIO；EACCES；以及 `removeHistory` 在另一个进程里刚删掉该文件的 ENOENT）。隔离用的 `Rename` 是持久的，且 `sweepAux()` 只在 `olderThanDay` 后才删 `.corrupt`，期间 `send-history` 再也看不到这条记录。
- 触发条件：并发大量 `send-*` 查询 + 大目录 ReadDir 期间 fd 紧张；或用户在另一个 UI 会话里 `send-delete` 与 `send-history` 竞争；或存储瞬时 I/O 错误。
- 影响：传输历史静默少一条（用户可见：刚发完的文件从历史里消失，且 `.corrupt` 残留一天）；若是 `send-status <id>` 命中，用户会看到 “no such transfer” 而记录其实是好的。崩溃恢复语义也因此不可信（分不清“真损坏”和“暂时读不到”）。
- 证据：待核实（代码路径确定；未在 darwin 上稳定复现 EMFILE）。隔离 rename 的返回值被丢弃（`s.root.Rename(...)` 未检查错误），失败时条目原样留下又在下一轮重复尝试。
- 修复建议：区分错误类型——只有 `json.Unmarshal`/结构校验类错误（用一个具体哨兵错误包裹，例如 `errRecordCorrupt`）才 rename 隔离；`*os.PathError`/`syscall.EMFILE`/`ENOENT` 等直接 `continue`（ENOENT）或 `return err`（其余）。同时检查 `Rename` 的返回错误。

#### [P2] `stats-summary` 静默丢弃“JSON 合法但不可解码”的样本：流量统计可无声归零，且无任何诊断输出

- 问题：本次改动把“解码失败 → 返回错误”改成“返回 nil 跳过”，同时新增的 `numeric()` 又对 `iface/peers/uids` 做类型白名单。结果是：任何一条字段类型漂移的样本（tailscaled 版本升级、`rx` 变成字符串、`uids` 变成 map…）导致**整条样本**被丢，但调用方拿到的仍是一份“看起来正常”的汇总（数值偏小甚至全零），没有任何 `warnings`/`skipped` 计数。

- 影响：UI“流量”页曲线/排名静默变低或空白，用户无法区分“真的没流量”和“样本全被丢了”；排查时 `foxytail.stats query summary` 也只输出干净数字。属可观测性回归（改动前会显式报错）。
- 证据：已实证（代码）+ `stats_summary_test.go` 只覆盖了“跳过之后继续读后续行”，没有断言“跳过时如何上报”。`grep -rn "warnings" foxytail.stats` 零命中。
- 修复建议：`statsAccumulator` 增加 `Skipped int`/`Invalid int` 计数，随汇总一起输出（例如 `"skippedRows":N`），并在 `foxytail.stats` 的 `summary` 分支把非零值透传到 UI；同时保留“坏一行不阻塞其余”的行为。

#### [P2] 命名冲突修复路径退化为 O(10000 × 文件大小) 的全量哈希，可让 `receive` 撞穿 60s 超时并在中途被杀

- 位置：`native/foxyfiles/taildrop.go:317-341`

```go
for index := 0; index < 10000; index++ {
    candidate := name
    if index > 0 { ... candidate = fmt.Sprintf("%s-%d%s", ..., index, ext) }
    if err = inbox.Link(".taildrop/"+stage, candidate); err == nil { created = true
    } else if errors.Is(err, os.ErrExist) {
        existing, openErr := inbox.OpenFile(candidate, taildropReadFlags(), 0)
        ...
        if statErr == nil && info.Mode().IsRegular() && info.Size() == n {
            h := sha256.New()
            _, readErr := io.Copy(h, existing)      // 每个同名同大小候选都完整读一遍
            same = readErr == nil && string(h.Sum(nil)) == string(sum)
        }
```

- 问题：只要目标名字被占用且**大小相同**，就对那个文件做一次完整 SHA-256（最多 2 GiB）；最坏情况连续 10000 个候选都同大小 → 10000 × 2 GiB 读取。而 `cmd_file_receive` 用 `_op_exec 60` 限时 60 秒（`TransferService.java:87` 给的是 150s，shell 先到），进程会在循环中途被 SIGKILL。
- 触发条件：对端连续投递同名文件（Taildrop 的 `name-N.ext` 递增命名天然会制造同大小候选，例如整批同尺寸照片 `IMG_0001.jpg` 反复重发）；或私有卷里有大量同大小同名族文件。
- 影响：`receive` 被超时杀掉 → shell 报 “file-receive failed/cancelled”，此时已导入的文件（逐个原子发布，不会损坏）已经进了收件箱但 UI 没收到回执；未处理完的 drop 留在 shared，源不会被删（因为进程没走到删源）。用户看到“失败”，重试又从头扫描，形成长时间无响应。
- 证据：待核实（代码路径确定；未构造 10000 个同大小文件的实测计时）。
- 修复建议：① 只在 `index` 首次冲突时做哈希比对（用于崩溃修复），之后候选直接用 `Link` 探测，冲突就 `continue`；② 或者把“同名同内容”判定改为 `SameFile`/size+mtime 快速判定，仅在 `n` 较小（例如 ≤ 8 MiB）时做全量哈希；③ 把 10000 降到几十（10000 次 `Link` 本身在慢速存储上也很贵），并在超限时 `fail(name, "cannot create an unused private inbox filename")` 让诊断可见（依赖 P1 第二条的透传修复）。

#### [P3] 单次接收字节上限检查位置偏前，实际可导入 `maxReceiveBytes + maxReceiveSize`（6 GiB）

- 位置：`native/foxyfiles/taildrop.go:169-172`

```go
if importedBytes >= maxReceiveBytes {          // 检查在导入之前，未按“导入后”判断
    result.skip(name, "per-call receive byte limit reached")
    continue
}
```

- 问题/影响：`importedBytes` 在循环内按 `before.Size()` 累加，但判据是“导入前是否已超 4 GiB”，所以最后一轮仍可再导入一个 2 GiB 文件 → 单次调用最多写入 6 GiB；注释声称的 4 GiB 上限不成立。在 32 位设备/低容量卷上更容易触发 ENOSPC。用户可见后果：磁盘被意外写满的时间点比预期晚。
- 证据：已实证（代码）。修复建议：改为 `if importedBytes+before.Size() > maxReceiveBytes { skip... }`，或用 `if importedBytes >= maxReceiveBytes` 之后再比较待导入大小。

#### [P3] 32 位（armv7）构建下 `readStatsRow` 的 `int(uint32)` 可产生负长度并 panic

- 位置：`native/foxyfiles/stats.go:40-49`

```go

if length > statsMaxRowBytes { return errors.New("invalid sorted statistics row") }
```

- 问题：`.github/tools/build-native.sh:30-31` 用 `GOARCH="$arch" GOARM=7` 构建，存在 32 位产物；在 32 位上 `0x80000000` 以上转 `int` 为负，`> statsMaxRowBytes` 判据不成立。`row.body[:length]` 直接 panic，进程带 trace 退出（`stats-summary` 会变成 shell 的 `jerr`）。

- 影响：统计命令崩溃而非报错；重试无效（损坏的 chunk 每次重建，但源头是缓存/输入文件时可能反复）。
- 证据：待核实（未在 armv7 上跑）。修复建议：`if raw := binary.LittleEndian.Uint32(header[8:]); raw > statsMaxRowBytes { return errors.New(...) }`，先比 `uint32` 再转 `int`。

#### [P3] `stopTransfers` 为 `.corrupt` 与未知 id 写 `.cancel`，`sweepAux` 只在 24h 后清理

- 位置：`native/foxyfiles/transfer.go:311-334`

```go
case strings.HasSuffix(entry.Name(), ".corrupt"):
    id = strings.TrimSuffix(entry.Name(), ".corrupt")
...
if live, found := active[id]; found && !live { continue }
if err = store.requestCancel(id); err != nil { ... }
```

- 问题/影响：`.corrupt` 条目永远不在 `active` map 里（`records()` 已把它隔离），因此每次 `send-stop`（每次停服务，`foxytail.service:284`）都会给它写一个 `.cancel`；该 marker 因为 `hasRecord[id]==false` 被 `sweepAux` 判为 stale，但要等 `olderThanDay` 才删。长期停/启服务会在 `.transfers` 里留下成堆无主 marker（`sweepAux` 每轮都要 stat 一遍）。无数据损坏，仅残留与噪音。
- 证据：已实证（代码）。修复建议：`case ".corrupt"` 分支不要 `requestCancel`（该记录不可能有 worker），只在 `.json` 分支处理；或在写 marker 前先 `Lstat(id+".json")`。

#### [P3] `archiveSourceRoot("/sdcard")` 跳过了其余路径都有的 SameFile 稳定性校验

- 位置：`native/foxyfiles/root.go:45-60`（`path == "/sdcard"` 时直接返回 `root`）

- 问题/影响：`/sdcard` 是 `/storage/self/primary` 的符号链接，若会话期间挂载点被替换/重挂（多用户切换、FUSE 重启），这个 root 可能指向被替换的目录，而所有子路径（`openChildRoot`）都只校验相对 parent 的稳定性。属低概率、需要系统级变化，且 `/sdcard` 只用于读（browse/receive）。修复建议：把 `/sdcard` 也走一次 `openRealRoot` 的 Lstat+SameFile 校验（`os.OpenRoot` 会解析 symlink，`os.Lstat("/sdcard")` 会看到 symlink，因此需要改成对 `realpath` 结果做校验，或对比 `root.Stat(".")` 与 `os.Stat("/sdcard/.")`）。

## 功能闭环缺口

1. **`receive` 的诊断字段无人消费**（P1 第二条）：`skipped`/`skippedCount`/`failed`/`failedCount`/`warnings` 在 `foxytail.taildrop.sh`、`foxytail.webapi-taildrop.sh`、`webui/src/**`、`FileActions.java` 全仓库 grep 零命中。
2. **`exported` 只统计、不展示**：`cmd_file_receive` 输出 `{received, exported}`，但 `Files.tsx:76` 只判 `result.ok`，`exported < received`（导出到 Download 失败）对用户完全不可见；此时源文件已被删除，唯一副本还在私有收件箱里，用户不知道要去导出。
3. **超时预算与上限不匹配**：`cmd_file_receive` 用 `_op_exec 60`（60s），而单次允许 4 GiB；`TransferService.java:87` 给的是 150s。慢速存储/大量小文件时 shell 会先杀进程，此时已发布的文件进了收件箱却没有任何回执（UI 显示失败）。
4. **`file-delete`/`file-clear` 不清理 Taildrop 回执**，也不通知 foxyfiles，导致 P1 第一条的回执墓碑行为；`cmd_file_clear` 已特意保留 `.taildrop`，说明作者把回执当“去重状态”，但没有配套的失效路径。
5. **`receive-mode` 的状态机不在本模块**：`directReceiveMode` 只探测 LocalAPI 返回 `500 opens not allowed in direct mode`；一旦打补丁的 daemon 文案变化，`taildrop_confirm_direct` 会拒绝所有接收，错误归因到用户（“unlock shared storage and restart”），而不是版本不匹配。
6. **尚未有 `inbox` 容量可见性**：`maxInboxFiles=10000` 只在 `inbox-list` 超限时报错，UI 没有“已满 N%/剩余”提示，配合 P1 第二条会让接收失败变成黑箱。

## 已检查无问题

- **命令注入**：`spawnTransferWorker` 用 `exec.Command(executable, "send-worker", "--root", root, "--id", id)` + `ExtraFiles`，`Setsid`，全模块无 `sh -c`；`runReceiveMode`/`runTaildrop` 只走 flag 解析。
- **路径穿越 / zip-slip**：`extract` 的 `memberPath` 是精确白名单（`conf/foxytail.conf`、`conf/routes.conf`、`conf/context.conf`、`foxytail.tun.up/down`）+ 可选 `foxytail/` 前缀；`..` 组件、绝对路径、`O_EXCL` 写入、member 去重、`seen[key]` 均已覆盖。
- **归档炸弹 / tar 特殊文件**：`boundedReader` 限 2 MiB 展开；逐 512 字节物理校验 `block[156]` 只放 `TypeReg/TypeRegA/TypeDir`，拒 `Linkname`、拒超长 member、要求两个全零块并 drain 校验尾随数据、`compressed.ReadByte() != io.EOF` 拒尾随压缩数据；`parent.Mkdir(leaf,0700)` 要求 dest 不存在，失败 `RemoveAll` 回滚。
- **os.Root 封装**：写入/解包/删除/统计遍历全部通过 `*os.Root`；`openChildRoot` 做 Lstat+SameFile；`archive.go:183` 本次已从裸 `OpenRoot` 改为 `openChildRoot`。
- **文件名清洗方向一致**：Go 的 `plainName` 拒绝全部 `Cc`+`Cf`+`/`+`\`+空/`.`/`..`+>255 字节+非 UTF-8；shell `_file_name_codepoint_jq`（`foxytail.webapi-tools.sh:219`）与 `_file_name_valid`（`:221`）拒绝集是 Go 的**子集**。因此不会出现“Go 已经删了源、shell 再判非法”的方向性错配（这一点在 P1 第一条的前提下尤其重要）。
- **暂存目录权限**：`privateChild` Mkdir+Chmod 0700；`stageFile` 的 `.outgoing/<token>` 0700、`.data`/`.lease` 均经 Root 打开；`saveStatsCache` 0600+`O_EXCL`+`O_NOFOLLOW`；`loadStatsCache` 要求 `Perm()&0077==0`。
- **原子写**：`transferStore.save` 用 `.write-<token>` + `fullWrite`（短写视为错误）+ `Rename` + `syncRoot`；统计缓存同构；`stageFile` 先写 `.data` 再 `Rename` 到最终名并 `syncRoot` 两次。
- **发送侧身份校验**：`send-worker` 从 fd 3 继承 `active.lock` 并 `SameFile` 校验；`identity()` 用 `Dev+Ino+Size+ModTimeNano` 四元组，上传后再 `opened.unchanged()`；`validatePeer` 要求 peer API 主机必须是 `Node.Addresses` 里的精确单播 IP（`prefix.Bits()==BitLen()`）。
- **HTTP 客户端**：`newLocalAPI` 禁重定向（`ErrUseLastResponse`）、`DisableKeepAlives`、`MaxResponseHeaderBytes: 32<<10`、响应体限 64 KiB / 4 MiB，`request.ContentLength` 与实际 multipart 长度一致（`prefix+file.Size+suffix`），文件用 `io.NewSectionReader` 直读无中间 goroutine。
- **并发与锁**：`stageFile`/`maintain`/`stage-delete` 都用 `.lease` 独占锁；`maintain` 的 `collectStaleStage` 只在抢到 lease 后才清目录，`activePaths` 声明在飞 stage；`taildropLock` 用 `lockBusy` 区分“忙”与“错误”。
- **文件读取一致性**：`readInbox` 用 `CopyN(before.Size())` 并在结束后 `SameFile+Size+ModTime` 复核；`removeTaildropSource` 三重比对（SameFile+Size+ModTime）才删。
- **状态机字段对齐**：`transferFile`/`transfer` 的 JSON tag（`sentBytes`/`progressKnown`/`bytesPerSecond`/`peerId`/`peerIp`/`selfId`/`startedAt`/`updatedAt`）与 `Models.java:116-128`、`webui/src/types.ts:70-85` 完全一致；`Models.java:117` 的 `sent > size` 断言不会触发（Go 侧 `sent := min(max(event.Sent,0), file.Size)`）。
- **清空收件箱**：`cmd_file_clear` 跳过 `.taildrop`/`.outgoing`、只删非软链的普通文件、跳过非法名并计数；`_file_export_to_download` 用 `set -C` 独占创建、失败即清理、成功后 `am broadcast` 触发媒体扫描。
- **`inboxFileCount` 与 `appendEntry` 容量语义一致**：两者都以 `plainName` + `IsRegular` + 排除保留名计数（Go 的 `ReadDir` 在 `d_type==DT_UNKNOWN` 时会回退 `lstat`，不会在 FUSE/ext4 上误判）。
