# 模块 A 审查结论：native/foxydns（Go DNS 常驻进程 + v1.9.0 NFQUEUE 劫持模式）

- 审查对象：`native/foxydns`（独立 Go module，`go.mod` 独立），v1.9.0 工作区未提交改动（该目录 18 文件 +617/−48）
- 审查方式：全量读码 + 调用链 grep（`tailscale/scripts/*.sh`）+ `GOOS=linux GOARCH=arm64 go build`（通过）+ `GOOS=linux go vet ./...`（通过）+ 本机 darwin `go test ./...`（**41 个 linux-only 测试被静默跳过**，见 P2-3）
- 本机为 darwin，无法运行 NFQUEUE 实测；标「待核实」的条目是未在真机验证的推断，其余均有读码或命令证据
- **无 P0**：未发现可被普通 App 触发的崩溃/提权/数据泄漏路径；控制 socket(0600+instance 校验)、ownership journal(O_NOFOLLOW+属主+flock)、raw 注入(仅 root)均按最小权限设计

## P1

#### [P1] IPv6 报文只要带非零 Flow Label 就被 parser 拒绝，IPv6 侧 DNS 拦截整体失效（静默 fail-open）
- 位置：`native/foxydns/transport.go:150`
  ```go
  case 6:
      if len(packet) < 40 || packet[1]&0x0f != 0 || packet[2] != 0 || packet[3] != 0 {
          return t, false
      }
  ```
  （`packet[1]&0x0f | packet[2] | packet[3]` 正是 IPv6 头的 20 bit Flow Label，`163` 行注释却说「declines fragments, IPv6 extension headers and incomplete captures」——Flow Label 既不是扩展头也不是分片）
- 问题：BT8：Linux 默认 `net.ipv6.auto_flowlabels=1`（Documentation/networking/ip-sysctl.txt），且 socket 选项 `IPV6_AUTOFLOWLABEL` 默认开启，`ip6_make_flowlabel()` 在 `__ip6_append_data()` 阶段（**早于** NF_INET_LOCAL_OUT 钩子）就把 hash 写进 IPv6 头，因此本地发出的 UDP DNS 查询**普遍带非零 Flow Label**。这类报文在 `packetTuple` 处被判为「不支持」→ `observe()` 返回 `captured=false` → `captureDecision` 走 `transport_linux.go:301-302`
  ```go
  // Unsupported/untracked packets retain their original payload and path.
  return nfqueue.NfAccept, 0, false
  ```
  即**不打 mark、不做 NAT REDIRECT**。hijack 模式的 `decide()` 同理（`select_linux.go:151-155` 直接 `NfAccept`）。
- 影响：设备 DNS 服务器为 IPv6 时（Android 双栈/仅 IPv6 网络、RA 下发的 IPv6 RDNSS 很常见），`A` 和 `AAAA` 查询**全部**不被拦截 → 查询直达公网解析器 → `<node>.<tailnet>.ts.net` 返回 NXDOMAIN。表现为「MagicDNS 全面失效」，而 IPv4 DNS 正常，排障时极难定位。因为是 fail-open，用户看到的是「解析不到」而不是「卡住」。
- 证据：读码 + Linux 内核 flowlabel 生成时序（内核 `ip6_make_flowlabel` 在 LOCAL_OUT 之前）。**待核实**：目标 Android 内核/ROM 是否把 `auto_flowlabels` 置 0（若置 0 则该分支不触发，但任何显式设置 Flow Label 的 App 仍会漏拦截）。
- 修复建议：删除这 3 个字节判断，只保留长度与 `packet[6]`（Next Header）判定；Flow Label 不参与 tuple，无需校验。
  ```go
  case 6:
      if len(packet) < 40 {
          return t, false
      }
  ```
  若确有意排除扩展头，应改为显式白名单：`packet[6]` 必须为 17 或 6（现有 `switch t.protocol` 已覆盖），不要用「整个头必须全零」来代替。

#### [P1] transparent 模式：任何一次内核瞬时错误都会 latch 成永久失败，并立刻对所有 DNS 返回 NfDrop（设备级 DNS 黑洞 2–4 秒）
- 位置：`native/foxydns/transport_linux.go:291-297`（结合 `transport_linux.go:273-276`、`select_linux.go:71-77` 的 first-error-wins）
  ```go
  if i.Health() != nil {
      return nfqueue.NfDrop, 0, false
  }
  mark, captured := i.observe(a)
  if i.Health() != nil {
      return nfqueue.NfDrop, 0, false
  }
  ```
  ```go
  func (s *Selector) setError(err error) {   // transport_linux.go 同构
      s.mu.Lock()
      if s.err == nil { s.err = err }        // 只写第一次，永不恢复
      s.mu.Unlock()
  }
  ```
- 问题：`setError` 是「首次错误永久锁存」，而 `captureDecision` 在锁存后对**每一个**报文返回 `NfDrop`，不是 `NfAccept`。可触发点包括：`SetVerdictWithOption` 失败（ENOBUFS/ENOMEM/netlink 忙）、`socketDiagCapabilityFailure`、`routeCapabilityFailure`、conntrack 查询失败（`transport_linux.go:456-458`）、journal 写失败、以及 mark 冲突。内核瞬时缺页/netlink 抖动即可命中。
- 影响：一次瞬时错误 → 该进程存活期间**所有** DNS 被主动丢弃。队列的 `NfQaCfgFlagFailOpen` 只覆盖「队列溢出」，覆盖不了显式 verdict；`--queue-bypass` 只在「无人持有该队列」时生效，而进程还活着。恢复只能靠 shell 侧 `foxydns watch` 轮询：`health.go:157` `time.Sleep(2*time.Second)` + `readHealth` 2 秒 deadline + `transport_linux.go:376` 的 guard 判定，即 **2–4 秒全校 DNS 中断**（`DNS_MODE=transparent` 用户）。hijack 模式此路径是 `NfAccept`（fail-open），行为正确——两者不一致本身说明 transparent 分支写成了 fail-close。
- 证据：读码（`captureDecision` 全部返回路径 + `setError` 单次写入 + `health.go` watch 轮询周期）。实测需真机注入一次 netlink 错误，**待核实**具体恢复时间。
- 修复建议：`captureDecision` 在 `Health() != nil` 时返回 `NfAccept, 0, false`（此时 iptables 规则仍在，放行 = 回退到系统 DNS，比黑洞好），把「拆除规则」交给 guard；guard 轮询周期从 2s 降到 500ms，或改成 `readHealth` 连续 2 次失败才退出。若要保留「能力丢失必须停用」的语义，至少区分「致命能力丢失」（EPERM/EACCES/EPROTONOSUPPORT，确实不该继续）与「瞬时 IO 错误」（ENOBUFS/ENOMEM，应重试）。

#### [P1] hijack 模式完全不拦截 TCP/53：TC 截断后的 TCP 重试与 TCP-first 解析器绕过 MagicDNS 并拿到 NXDOMAIN
- 位置：`tailscale/scripts/foxytail.dns-modern.sh:290-291`（hijack 只装 UDP 规则）+ `native/foxydns/transport.go:192-196`（`udpQueryPayload` 强制 `tuple.protocol == 17`）
  ```sh
  "${_hf_cmd}" -w 2 -t mangle -A "${MODERN_QUEUE_CHAIN}" -p udp --dport 53 \
    -j NFQUEUE --queue-num "${MODERN_QUEUE}" --queue-bypass || return 1
  ```
  ```go
  func udpQueryPayload(packet []byte) (flowTuple, []byte, bool) {
      tuple, ok := packetTuple(packet)
      if !ok || tuple.protocol != 17 { return flowTuple{}, nil, false }
  ```
- 问题：hijack 模式既不装 nat REDIRECT（`dns-modern.sh` 注释自述「no NAT redirect exists」），也不 queue TCP，因此 `TCP:53` 完全在拦截范围外。而 `select_linux.go:182-186` 会按客户端 EDNS0 size（上限 4096）`Truncate`，一旦某个 tailnet 名记录多到超过客户端 UDP 上限（`records.go` 单名不限 IP 数，`loadRecords` 上限 32768 条），应答带 `TC=1`；标准客户端（glibc/netd/dnsmasq）**必然改用 TCP 重试** → 该 TCP 查询直达真实解析器 → NXDOMAIN/NODATA，客户端拿到否定答案且不会再回退 UDP。
- 影响：记录多或客户端 EDNS0 size 小于 512 的极端情况（部分 IoT/老 App 不带 OPT，size=512）下，tailnet 名「偶发解析失败」，且失败是权威否定答案（比超时更难自愈）。RFC 7766「TCP-first」类客户端则 100% 失败。
- 证据：读码 + 脚本规则 grep（hijack 链只有 `-p udp`）。**待核实**：实际部署中是否有单名多 IP 导致 >512 的用例。
- 修复建议：二选一——(a) hijack 也 queue TCP（`-p tcp --dport 53`），`Selector.decide` 增加 TCP 分支（需处理 TCP 长度前缀、握手状态，成本高）；(b) 最小改动：`decide()` 在 `response.Truncated` 为真时**不要注入**，改 `NfAccept`（让原查询走真实解析器，至少与现状一致且不泄漏半截答案），并在 `records.answer` 里按 TTL 30s 限制单名 A/AAAA 条数（如 ≤ 8），从源头避免截断。推荐 (b)。

## P2

#### [P2] ownership journal 在新流路径上做 `fsync`，且持有 verdict 互斥锁——每个新 DNS 源端口的首包都付一次落盘延迟
- 位置：`native/foxydns/ownership_linux.go:139-147`，调用点 `native/foxydns/transport_linux.go:393-401`
  ```go
  // Persist before the marked verdict. A killed helper must not orphan DNAT.
  if err := json.NewEncoder(j.file).Encode(f); err != nil { return err }
  if err := j.file.Sync(); err != nil { return err }
  ```
  ```go
  if i.ownership != nil {
      if err := i.ownership.record(tuple, ct.ID); err != nil {
  ```
- 问题：`record()` 在 `i.mu`（`observe()` 持锁）且 `i.verdictMu`（`capture()` 持锁）内执行 `Sync()`。DNS 客户端普遍每查询换源端口（netd/glibc 行为），因此**几乎每个查询都是「新流」**，都要一次 4KB 写 + fsync。eMMC/UFS 在 writeback 压力下 fsync 可达 10–100ms，期间所有排队报文拿不到 verdict。
- 影响：DNS 首包延迟抖动 + 突发查询（App 启动并发解析）时队列逼近 `MaxQueueLen 512`，溢出后 `FailOpen` 放行 → 未打 mark → 不重定向 → tailnet 名落到公网解析器。表现为「App 启动时偶尔解析失败」。
- 证据：读码（锁序 `verdictMu → i.mu → j.mu`，`Sync()` 在两者内层）。实测需要真机 fsync 延迟采样，**待核实**。
- 修复建议：改成 group commit —— `record()` 只 append 到内存队列并立即返回，由一个后台 goroutine 每 50ms（或每 32 条）批量 `Write`+一次 `Sync`；`capture()` 在 mark 之前只等「已入队」。若坚持「先落盘后 verdict」，可退回 `fdatasync` + 只在 `Close()`/`quiesce()` 时强制 `Sync`，并把失败降级为日志（journal 丢几条只会留下超时自愈的 conntrack 条目，不会造成规则残留）。

#### [P2] NXDOMAIN 不带 SOA（也不带 RA），否定答案会被中间 stub 缓存，tailnet 节点上线后仍否定数分钟
- 位置：`native/foxydns/records.go:156`
  ```go
  if !known && !reverse {
      response.Rcode = dns.RcodeNameError   // NXDOMAIN，无 SOA
  }
  ```
  `grep -n "SOA" native/foxydns/*.go` → 无任何 `dns.SOA`；`grep -n RecursionAvailable` → 无（`SetReply` 后 RA 恒为 0，仅 `Authoritative=true`）
- 问题：RFC 2308 §5 规定否定答案的缓存时长取自 authority 段 SOA 的 MINIMUM（或 SOA TTL 与 MINIMUM 的较小值）；没有 SOA 时，转发/缓存型 stub（dnsmasq、netd 的 DnsResolver、部分 OEM DNS 代理）会用自身默认否定 TTL（常见 300–900s）缓存该 NXDOMAIN。`recordTTL=30` 只作用于正记录，对否定答案无效。
- 影响：`tailscaled` 尚未上报新节点、或 `DNS_CONTEXT_FILE` 尚未被 shell 重写时产生的 NXDOMAIN，会在本地缓存里存活数分钟：节点上线后 App 仍然「解析不到该域名」，只能等缓存过期或清 DNS 缓存。用户可见、可稳定复现（先断开 tailnet 触发一次 NXDOMAIN，再连接）。
- 证据：读码 + grep（包内无 SOA 构造）。缓存时长取决于 stub 实现，**待核实**具体值。
- 修复建议：在 NXDOMAIN 分支追加一条 SOA（`NS=<suffix>, Mbox=hostmaster.<suffix>, Serial=1, Refresh=30, Retry=30, Expire=60, Minttl=recordTTL`）放入 `response.Ns`；同时把 `RecursionAvailable` 显式设为 `false` 之外的语义（见 P3）。SOA 的 `Minttl` 必须等于 `recordTTL`(30)，否则否定缓存会比正向 TTL 长。

#### [P2] `a.UID == 0` 守卫在 Fchown 之后对「helper 自己的上游查询」永久失效——防自环只剩 iptables 一条命
- 位置：`native/foxydns/transport_linux.go:283`（`select_linux.go:135` 同构）
  ```go
  if a.UID != nil && *a.UID == 0 && a.GID != nil && *a.GID == helperSocketGID {
      return nfqueue.NfAccept, 0, false
  }
  ```
  对比 `native/foxydns/transport_linux.go:704`
  ```go
  if err := unix.Fchown(fd, int(uid), -1); err != nil {   // uid = 原始 App 的 uid
  ```
- 问题：NFQUEUE 的 `NFQA_UID/NFQA_GID` 取自 `SOCK_INODE(sk)->i_uid/i_gid`；`Fchown(fd, appUID, -1)` 把上游 socket 的 inode uid 改成了 App 的 uid（gid 保持 65533）。因此 helper 自己转发出去的查询在队列里看到的是 `UID=appUID`，`*a.UID == 0` 恒不成立，该守卫对「最需要它的那类报文」完全失效。真正阻止自环的是 mangle/nat 里 `-m owner --uid-owner 0 --gid-owner $MODERN_UPSTREAM_GID -j RETURN`（xt_owner 读 `filp->f_cred->fsuid/fsgid`，即建 socket 时的文件凭据，未受 Fchown 影响）。注释「keep the helper credential guard in step with the iptables exemption」的假设不成立。
- 影响：当前规则齐全时无可见问题（双保险变单保险）。一旦 RETURN 规则缺失/被 OEM 规则覆盖/`MODERN_UPSTREAM_GID` 不匹配（例如脚本变量被改写，`modern_rules_present` 只在启动时校验一次），helper 会把**自己转发的查询**判定为 `captured=true` → 打 mark → NAT REDIRECT 回 127.0.0.1:53 → `Lookup` 命中刚写入的 flow → 再 dial 再转发 → 自激循环（每层 1 socket + 1 conntrack + 5s ctx），直到 fd 耗尽。
- 证据：读码（内核 `nfqnl_build_packet_message` 用 `sock_i_uid/sock_i_gid`；`sockfs_setattr` 会同步 `sk_uid`）；`setSocketContext` 只改 uid 不改 gid。自环路径未实测，**待核实**。
- 修复建议：守卫去掉 uid 合取，只用 gid（`Fchown(...,-1)` 不动 gid）：
  ```go
  if a.GID != nil && *a.GID == helperSocketGID { ... NfAccept ... }
  ```
  或在 `Lookup()` 里加一条硬断言：命中 flow 时若其 socket inode/cookie 属于本进程自己（记录 `DialOriginal` 创建的 socket inode 集合），直接 `ErrFlowContext` 返回，从根上断开自环。

#### [P2] linux-only 测试在本机全量静默跳过，v1.9.0 的整条 NFQUEUE 新链路零可执行覆盖（绿灯假象）
- 位置：`native/foxydns/{select_linux_test.go,transport_linux_test.go,transport_diag_linux_test.go,transport_route_linux_test.go,ownership_linux_test.go,transport_e2e_linux_test.go,ownership_e2e_linux_test.go}` 均带 `//go:build linux`；本机 darwin 存在 `select_other.go`/`transport_other.go`/`ownership_other.go` 桩，使包仍能编译、非 linux 测试仍能跑
- 问题：本机 `go test ./...` 输出 `ok github.com/.../foxydns (cached)`，但实际被跳过 41 个用例：`select_linux_test.go` 10、`transport_linux_test.go` 15、`ownership_linux_test.go` 5、`transport_diag_linux_test.go` 5、`transport_route_linux_test.go` 3、`transport_e2e_linux_test.go` 1、`ownership_e2e_linux_test.go` 1。v1.9.0 的核心新逻辑（`packetTuple`/`udpQueryPayload` 边界、verdict 全分支、mark 应用、conntrack decode、inject 校验和）**只在 Linux 上可执行**，而 darwin 上 `NewSelector`/`NewInterceptor` 直接用桩返回 `ErrUnsupported`，`server_test.go`(625 行，+271) 里对 hijack 分支的断言实际测的是桩返回路径。
- 影响：`go test ./...` 在开发机/多数 CI 上永远绿，P1-1（flow label）、P1-3（TCP）、P2-1（fsync）这类问题不会被测试发现；reviewer 也容易被「有 15 个 transport 测试」误导。
- 证据：命令输出（`go test ./...` → ok cached；`grep -l "go:build linux" *_test.go` → 7 个文件；`grep -c "^func Test"` 计数）；`GOOS=linux go build/vet` 通过说明编译期覆盖 ≠ 运行期覆盖。
- 修复建议：CI 增加 `GOOS=linux go test -c` + 在 Linux runner（或 `docker run --privileged` 里的 Linux 容器）执行，至少跑不带 NFQUEUE 的那部分（`packetTuple`/`records.answer`/`healthState`/config 解析）；把 `packetTuple`/`udpQueryPayload`/`injectUDP` 的构造与校验和部分抽到无 `//go:build` 的纯函数文件（它们不依赖 netlink），让这些边界用例在 darwin 也能跑。特别建议补：带 Flow Label 的 IPv6 包、IHL>5 带 options 的 IPv4 包、`end < len(packet)` 的尾填充包、`udp.length != end-offset` 的包。

## P3

#### [P3] `serveHealth` 的 TXT 应答既不 Truncate 也不带 EDNS0 OPT，是全包唯一条无界应答路径
- 位置：`native/foxydns/health.go:67-83`（`data, _ := json.Marshal(r.health())` → base64 → 每 255 字节切一个 TXT string → `w.WriteMsg(response)`，全程无 `response.Truncate(...)`、无 `SetEdns0`）
- 问题：`state.Error` 字段（`health.go:29`，取自 `queueError.Error()`，netlink 错误串可能很长）直接进 JSON → base64 膨胀 1.33 倍 → 单一 TXT RR 可远超 512 字节。与包内其它所有应答路径（`server.go:82`、`select_linux.go:181` 都 `Truncate` 到客户端 EDNS0/4096）风格不一致；一旦总量接近 64KB，`Pack()` 直接失败，健康检查持续失败 → `queueReady=false` → guard 误判「capability 丢失」并拆掉 iptables。
- 影响：错误信息越长越可能触发；触发时中断的是**健康的**捕获链路（误杀）。目前阈值很高，属潜在风险。
- 证据：读码 + grep（`Truncate` 只出现在 `server.go`/`select_linux.go`）。
- 修复建议：`health.go` 里对 `r.health()` 的 JSON 做定长裁剪（`state.Error = truncate(err, 256)`），并在 `WriteMsg` 前 `response.Truncate(dns.MinMsgSize)`；同时把 query 的 OPT 回显（`response.SetEdns0(4096,false)`）以符合 RFC 6891 §6.2.3。

#### [P3] 本地应答 `RA=0` 且 `SetReply` 后未显式设置，部分链路会把它当作非递归服务器
- 位置：`native/foxydns/records.go`（`answer()` 内 `response.SetReply(q)` + `Authoritative = true`，无 `RecursionAvailable`；`grep RecursionAvailable` → 无）
- 问题：对 `<tailnet>.ts.net` 的本地答案 `AA=1, RA=0` 是自洽的，但对**同一个监听器**转发来的上游应答（`server.go` 直接把上游 response 写回）通常是 `AA=0, RA=1`，同一 socket 上两种语义并存。个别转发器（systemd-resolved 风格）会在 `RA=0` 时把该服务器标为「非递归」并从候选列表降权。
- 影响：多解析器选择场景下自身被降权，实际 Android netd 不检查 RA，风险低。
- 证据：读码；影响面**待核实**。
- 修复建议：本地应答显式 `response.RecursionAvailable = false`（表达「这是权威本地答案」），或在 `serveHealth` 之外的统一出口明确该服务是「递归+权威混合」，避免依赖 `SetReply` 的默认值。

#### [P3] hijack 与 transparent 对「自己的报文」判断口径不一致
- 位置：`native/foxydns/select_linux.go:135` vs `transport_linux.go:283`（两处 uid/gid 守卫相同），但 `transport_linux.go:700-724` 的 `setSocketContext` 只在 transparent 生效
- 问题：同一段守卫在两种模式下的真实语义不同（hijack 从不 Fchown，因此守卫有效；transparent 失效，见 P2-3）。读代码时容易误判「两种模式都有双保险」。
- 影响：维护期误判，非用户可见缺陷。
- 证据：读码。
- 修复建议：按 P2-3 统一为 gid-only，并加注释说明「transparent 模式下 uid 会被 Fchown 改写」。

#### [P3] 重复 `serve` 实例在队列被占用时仍然「半启动成功」
- 位置：`native/foxydns/server.go:185-201`（`NewInterceptor`/`newSelector` 失败只记 `queueError`，`startService` 仍继续 `writeState(true)`），`select_linux.go:47-61` 用 `queueRegistrationError(err)` 包装的错误未在 `serve` 路径上变成退出码
- 问题：双实例时第二个进程 `nfqueue.Open` 得到 EBUSY，但仍在 127.0.0.1:53（若端口不同）或已绑端口上起服务，`.ready=true, .queueReady=false`。shell 侧 `dns-modern.sh:570-571` 会因 `!queue_ready` 判失败并回退，因此**不构成生产问题**，但 `serve` 自身没有 fail-fast。
- 影响：日志里出现「启动成功」后紧跟 guard 拆链的噪声，排障时误导。
- 证据：读码（`startService` 成功路径 + 脚本 570-571 的二次校验）。
- 修复建议：`mode != local` 且 capture 初始化失败时，`startService` 直接返回错误（exit 1），由 shell 走既有的降级判定。

## 已检查但无问题的区域（避免重复审）

| 区域 | 结论 |
|---|---|
| `inject_linux.go` 校验和/长度 | `udpChecksum4` 伪头 12 字节（`pseudo[9]=17`，len@[10:12]）、`udpChecksum6` 40 字节伪头（len@[32:36]，`pseudo[39]=17`）布局正确；`0xffff-28` 上界对 IPv4(20+8) 精确、对 IPv6(40+8) 偏松但不越界；0 校验和 → `0xffff` 符合 RFC 768；`checksumSum` 的跨段奇字节处理正确；IP 头 checksum/ID 留 0 依赖 `IPPROTO_RAW` 隐含 `IP_HDRINCL`（内核 `raw_send_hdrinc` 会填 id 与 ip_sum），注释与实现一致；`injectSelfTest` 端到端验证了伪造源投递（含内核校验和验证），实际拦住任何校验和错误 |
| verdict 完备性 | `Selector.decide`/`Interceptor.captureDecision` 所有分支（nil PacketID 除外，此时无包可判）都返回 `NfAccept`/`NfDrop`，无漏 verdict；`capture()` 的 `return 1` 只在 `SetVerdict` 自身失败时出现（见 P1-2 的后果讨论） |
| `--queue-bypass` 与规则残留 | 三处 NFQUEUE 规则全部带 `--queue-bypass`（`dns-modern.sh:235,264,291,303`）；nat 链在 mangle 队列之前挂载、拆除时先拆拦截后拆队列（`:239-245`）；`modern_rules_present/present` 做「必须是 OUTPUT 最后一条/第一条」的顺序校验；`--queue-bypass` 保证「进程已死但规则未拆」时回落到 ACCEPT。**无残留黑洞** |
| capture mark 设计 | `0x20000000` 只在 accept verdict 上打（`transport_linux.go:299`），因此「进程死了但 nat 规则还在」不会重定向（没人打 mark）；`observe()` 里 `ct.Status.DstNATDone() && !ownership.contains()` 会让既有第三方 DNAT 流放行（`:336`）；`intact()` 要求 `Mark&captureMark == 0`（`transport.go:46`）。设计自洽 |
| `config.go` 解析边界 | `io.LimitReader(f, 65537)` + `DisallowUnknownFields` + 单对象校验；`Listen` 必须是 `127.0.0.1`；端口 0–65535；`Mode ∈ {local,transparent,hijack}`；`transparent/hijack` 强制 `Queue != 0`；`ContextFile`/`StateFile` 绝对路径；`OwnershipFile` 仅 transparent 要求；`writeJSON` = 同目录 CreateTemp + Sync + Rename（原子） |
| `main.go` 参数覆盖 | `--queue` 用 `flags.Visit` 区分「显式传入」与默认值 1053，再校验 1–65535（`main.go:88-99`）；`--state` 覆盖后重新 `validate()`；`probe --hijack` 与 `modern_probe_hijack` 的 `.ok/.queue/.inject` 三字段**完全对齐**；`probe`(transparent) 的 `.ok/.queue/.conntrack/.socketContext` 与 `modern_probe_capabilities` 对齐 |
| typed-nil 修复 | `server.go:187` `if interceptor == nil` + `:198-201` `var selector *Selector; ...; if selector != nil { s.interceptor = selector }` 两处都挡住了「typed nil 装进 interface → `Health()` 解引用 nil 指针」的崩溃；`healthState`（`:268-275`）另有一层 `s.interceptor != nil` 兜底，`control.go:60-63` 同。**该 bug 已闭环** |
| `Interceptor.track/observe` 锁与错误 | first-error-wins 在 `observe()` 内联写 `i.err`（注释说明已在 `i.mu` 内，避免重入死锁）；锁序恒为 `verdictMu → i.mu → j.mu`，无反向获取 |
| 优雅退出 | `serve` SIGTERM/SIGINT：transparent 走 `shutdownCapture()`（3 次尝试、100ms 间隔：quiesce → cleanupOwned）；hijack 直接返回，`defer s.Close()` 关队列；shell 侧 `modern_stop_process` 顺序为「先拆规则 → 再 SIGTERM」，配合 `--queue-bypass` 无窗口。`service.Close()` 用 once 保护，`Selector.Close()` 自带 `s.closed` 短路（`select_linux.go:94-104`），重复 Close 安全 |
