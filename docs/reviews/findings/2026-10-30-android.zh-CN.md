## P1

#### [P1] E-01 `RootApi` 超时只发后端 cancel，不强杀进程：卡住的 mutation 会永久占用控制台

- 位置：`android/app/src/main/java/dev/foxderin/tail/RootApi.java:163`

```java
ScheduledFuture<?> timer = CLOCK.schedule(() -> {
    call.timedOut = true;
    call.cancel();
}, seconds, TimeUnit.SECONDS);
```

  `android/app/src/main/java/dev/foxderin/tail/RootApi.java:96-112`（`Call.cancel()` 主体）

```java
if (request == null || context == null) {
    if (localCancellation) IO.execute(this::stop);
    return;
}
// 否则：向后端投递 "cancel" 请求，只有后端回答 cancelled==true 才 stop()
if (result.optBoolean("cancelled") && !finished) stop();
```

  `android/app/src/main/java/dev/foxderin/tail/RootApi.java:184`

```java
int exit = process.waitFor();
```

- 问题机理：`execute()` 的超时只把 `timedOut` 置位并调用 `cancel()`；而 `cancel()` 对"已启动且不在 `localCancellationAllowed` 白名单内"的命令**没有任何本地兜底**——它把取消交给后端 socket 协议，然后 `if (result.optBoolean("cancelled") && !finished) stop()`。同理 `waitFor()` 是无限等待。于是超时到点后调用线程既不返回、也不销毁进程，只能等后端自己吐结果。
- 触发条件：`localCancellationAllowed` 黑白名单（`RootApi.java:206-212`）明确排除所有 mutation，即 `file-stage`、`file-send-start`、`file-receive`、`restore`、`backup`、`settings-set`、`routes-set`、`context-set`、`serve-set`… 任一后端阻塞（daemon 锁竞争、`tailscale` 命令挂死、备份 tar 卡在慢 SD 卡、用户中途撤销 root）都命中。
- 用户可见影响：`ControlClient.submit()` 把 `submitting=true` 置上（`ControlClient.java:195`），此后 `busy()` 恒为 true → 所有 mutation 被 `control_busy` 拒绝、`control.mutate` 全部失败；`TransferService` 用的是单线程 `EXECUTOR`，一次卡死的 `file-stage` 就让"文件发送"永久停在通知里，取消按钮也只发一个后端 cancel。恢复唯一手段是杀进程。
- 证据：已实证（代码路径闭合）。`androidTest/.../ControlChecks.java` 里断言 `"Accepted mutation stays owned until completion"` 与 `!RootApi.localCancellationAllowed("operation-start"|"login"|"file-send-start")`，说明"不强杀"是刻意的——但**没有任何独立于 `cancel()` 的死线**，刻意与无限等待是两件事。
- 修复建议：
  1. 超时到点后保留"优雅取消"窗口（如 5 s），窗口结束无条件 `process.destroy()`，再 2 s 后 `destroyForcibly()`，并让 `waitFor()` 换成 `waitFor(grace, TimeUnit.SECONDS)`。
  2. 返回值上区分三种终态：`cancelled`（后端确认）、`unknown`（本地强杀/超时，结果不明）、`ok`。强杀路径应合成 `{"ok":false,"unknown":true,"error":...}`，让 `ControlClient.markUnknown` 接管而不是继续等。
  3. `TransferService` 侧对 `file-stage`/`file-send-start` 单独设硬超时，超时后进入 `unknown` 并把 `prefs "unknown"=true` 写掉，否则用户会被 `requireNoTransfers` 永久锁死（见 E-05）。

#### [P1] E-02 `ControlClient` 轮询在 Activity 关闭后继续，每秒拉起一次 `su`

- 位置：`android/app/src/main/java/dev/foxderin/tail/ControlClient.java:115-118`

```java
void removeListener(Runnable listener) {
    listeners.remove(listener);
    if (listeners.isEmpty() && !busy()) main.removeCallbacks(poll);
}
```

  `android/app/src/main/java/dev/foxderin/tail/ControlClient.java:228-236`

```java
private void markUnknown(Exception error) {
    ...
    main.removeCallbacks(poll);
    main.postDelayed(poll, 3000);
}
```

  `android/app/src/main/java/dev/foxderin/tail/ControlClient.java:237-239`

```java
void reconnect() {
    main.removeCallbacks(poll);
    if (id == null || polling || submitting) return;
```

- 问题机理：`busy()` 定义为 `id != null || submitting`（`ControlClient.java:69`），而 `id` 从 SharedPreferences 恢复、只在操作终态清理。`removeListener` 只有 `!busy()` 时才 `removeCallbacks(poll)`；`ControlClient` 是进程级单例（`ControlClient.java:19-23`），`WebBridge.destroy()` 只是 `control.removeListener(changed)`，**不会停掉已排队的 poll**。只要存在一个非终态的 operation id（后端 socket 断开、operation 长期 `running`、`markUnknown` 分支），每次 poll 失败都会再 `postDelayed(poll, 3000)`，poll 内部是 `RootApi.json(..., "operation-status", expected)`——即每次都是一次 `su -c /system/bin/sh foxytail.webapi.sh` 进程。
- 触发条件：提交 mutation 后进程未被杀但 operation 停在 running/unknown（例如后端 daemon 重启、socket 半开），用户退出控制台或旋转返回桌面。
- 用户可见影响：应用退到后台后仍 1–3 s 一次 root 进程；Magisk/KernelSU 授权日志、logcat、耗电都会异常；某些 ROM 的"后台高频 su"会直接弹授权提示或杀进程。
- 证据：已实证（`removeListener` / `markUnknown` / `reconnect` 三者组合闭合），未上真机计时。
- 修复建议：`removeListener` 在 `listeners.isEmpty()` 时无条件 `main.removeCallbacks(poll)`，并把"是否继续轮询"交给下一次 `addListener → reconnect()`；`markUnknown` 的 3 s 重试加上限与指数退避（如 3 s×2ⁿ，上限 60 s，最多 N 次）；`WebBridge.destroy()` 额外调用 `control.suspend()`（新增）落一次 `removeCallbacks` + `polling` 复位。

#### [P1] E-03 草稿密钥拦截只匹配 key 名，换个键名即可写入；且错误串硬编码英文

- 位置：`android/app/src/main/java/dev/foxderin/tail/ControlActivity.java:220-233`

```java
private void checkDraft(String key, Object value) throws IOException {
    if (key != null && key.toLowerCase(java.util.Locale.ROOT)
            .matches(".*(authkey|password|credential|secret|sourceuri|token|key|apikey|passwd|auth).*"))
        throw new IOException("Credentials and source URIs cannot be saved as drafts");
    ...
    if (value instanceof String && ((String) value).startsWith("content://"))
        throw new IOException("Source URIs cannot be saved as drafts");
```

- 问题机理：这是**结构性白名单缺失**：拦截依据是字段名，值只额外挡了 `content://` 前缀。前端 `bindNativeDraft()`（`webui/src/settings.ts:44-69`）把整个页面 snapshot 原样作为 `value` 提交，页面状态里任何字段（例如 `{"v":"tskey-auth-…"}`、`{"server":"https://…","k":"<auth key>"}`）都能落进草稿，随后经 `onSaveInstanceState`（`ControlActivity.java:254-267`）进入系统 `Bundle`（`ActivityClientRecord` 在 system_server 内存里），并在 `app.bootstrap`（`WebBridge.java:158-164`）中原样回给页面。
- 触发条件：任何插件式/新增页面字段命名不含 `key/auth/token/secret`（当前 `snapshot()` 形状由各页面自由决定，`settings.ts` 只约束 key 是 8 个页面名之一）。旋转屏幕或进程被系统回收后从草稿恢复，密钥重新出现在输入框。
- 用户可见影响：控制台"草稿不落密钥"的承诺不成立；密钥可能出现在系统保存的 Activity 状态、`dumpsys activity` 输出、以及恢复后的 UI 明文。同时该正则扩宽后存在误伤面（任何键名含 `key`/`auth` 子串，如 `keys`、`authMode`、`hotkeys`），会把合法草稿整页拒掉；错误文案走硬编码英文，中文界面显示英文（`res/values-zh` 里不存在该串）。
- 证据：已实证（正则与 value 检查分支均已读全）。测试覆盖也不足：`androidTest/.../WebViewChecks.java:45` 只用一个 `authKey` 键做正向拒绝用例，没有"换个键名仍被拒"的负向用例。
- 修复建议：
  1. 反向做**白名单**：草稿只允许"UI 状态"字段（筛选、排序、滚动位置、标签页、开关状态），用显式 schema 校验；或直接放弃通用草稿，改由前端只提交非敏感子集。
  2. 若要保留通用草稿，追加**值侧扫描**：`tskey-`/`auth-` 前缀、长度 > 64 的 base64/hex 串、包含 `://` 的 URL/URI、`\n` 分隔的多行密钥；命中即拒绝。
  3. 错误串移入 `res/values*/control_common.xml`，并在 `WebViewChecks` 里补"键名伪装 / 值伪装 / 合法草稿不被误伤"三组用例。

#### [P2] E-04 旋转屏幕会取消未提交的文件导出（`FileActions.destroy`）

- 位置：`android/app/src/main/java/dev/foxderin/tail/FileActions.java:433`

```java
if (export != null && export.owner.get() == this) { export.reply = null; if (!export.committing) export.cancel(); export.owner.clear(); }
```

- 问题机理：`ExportJob` 用 `WeakReference<FileActions> owner` + 静态 `export` 设计成"可跨重建存活"（`FileActions.java:19-21`、`:444-509`），但 `destroy()` 在**每次**销毁都把 `owner.get() == this` 的导出取消掉。旋转后旧实例销毁 → 正在 `cache()`/复制中的导出被 `cancel()`，`committing` 之后的路径才被保护。同一方法里 URI 释放却用 `if (activity.isFinishing())` 区分"真退出"和"重建"，两处语义不一致。
- 触发条件：文件导出（`artifact.save` / `files.save` / `files.share`，即 `Downloads` 导出或分享缓存）进行中旋转屏幕、切换深色模式（部分 ROM 会重建）、或系统回收 Activity。
- 用户可见影响：导出静默中止，前端 `files.save`/`artifact.save` 的 Promise 拿不到终态（配合 E-09 永久 pending），进度条停在某个百分比；用户以为导出成功。
- 证据：已实证（代码路径闭合）。`androidTest/.../FilesIntegrationChecks.java` 有 save commit-fence 测试，但没有"重建期间导出存活"的用例。
- 修复建议：`destroy()` 里只在 `activity.isFinishing()`（或 `!activity.isChangingConfigurations()` 且非重建）时取消；重建路径只 `export.reply = null` 并保留 `owner` 空引用，让新 `FileActions` 在 `attach` 时通过静态 `export` 重新接管（`ExportJob.changed()` 已经通过 `owner.get()` 做了空检查，天然支持）。

#### [P2] E-05 `TransferService.onTimeout` 不 cancel、不置 unknown，`running=false` 与仍在跑的 worker 不一致

- 位置：`android/app/src/main/java/dev/foxderin/tail/TransferService.java:261-265`

```java
@Override public void onTimeout(int startId, int fgsType) {
    stopping = true; running = false;
    prefs.edit().putString("message", getString(R.string.service_timeout)).putBoolean("busy", false).apply();
    stopForeground(STOP_FOREGROUND_REMOVE); stopSelf();
}
```

- 问题机理：前台服务超时回调只改内存/偏好标志并停前台，**不向后端发 `file-send-cancel`、不置 `prefs "unknown"`、不中断 worker 线程**（worker 仍在 `EXECUTOR` 上跑 `file-stage`/`file-send-start`/1 s 轮询）。更糟的是它把 `prefs "busy"` 主动写成 `false`：`FileActions.transferBusy()` / `ControlClient.requireNoTransfers()` 因此认为"没有传输"，用户可立刻发起第二次传输，与仍在跑的 worker 并发写同一份 staged 文件与 job 状态；`unknown` 又不置位，历史里会出现两个 active job。
- 触发条件：Android 15+（`dataSync` 前台服务有 6 小时上限）大文件传输、或后端长时间无响应导致服务一直不结束。
- 用户可见影响：传输状态错乱、重复上传、staged 清理遗漏；用户看到"传输已结束"却又能立刻再发一次。
- 证据：已实证（`onTimeout` 与 `onDestroy` 对比，后者才会 `request.cancel()`）。未上真机触发（需要长时前台服务）。
- 修复建议：`onTimeout` 里按 `onDestroy` 的语义补齐：`request.cancel()`（若在跑）、`prefs "unknown"=true`、publish `service_timeout` 并保留 `running=true` 直到 worker 真正退出；只有 worker 结束后才 `stopSelf`。若无法保证，则改为"超时即进入 unknown 并要求用户 acknowledge"，与 `files.acknowledge` 前端流程对齐。

#### [P2] E-06 服务 busy 时静默丢弃 START/ADOPT/IMPORT intent，调用方已回 `accepted:true`

- 位置：`android/app/src/main/java/dev/foxderin/tail/TransferService.java:35-70`

```java
if (CANCEL.equals(action)) { ... }
if (!busy) startForeground(...);
if (busy) return START_NOT_STICKY;   // 后续 START / ADOPT / IMPORT / RECOVER 全部静默丢失
```

  `android/app/src/main/java/dev/foxderin/tail/FileActions.java:329-330`

```java
requestNotifications(); launch(intent); respond(reply, object("ok", true, "accepted", true));
```

- 问题机理：`send()` 在 `launch(intent)` 之后**同一个 UI 线程节拍里**就回 `accepted:true`；服务端 `busy` 时那一步直接返回、不广播失败、不写 `message`，前端只能靠后续 `files.snapshot` 里没有 job 来"猜"失败。
- 触发条件：`Activity` 重建后 `recover()`（`FileActions.java:374-400`）在已有传输进行时再次 `launch(ADOPT)`；或用户在两次快速点击之间触发第二次 `files.send`（`transferBusy()` 窗口之外）。
- 用户可见影响：ADOPT/取消恢复静默失效，界面停在"正在准备"；没有错误文案可显示（错误码矩阵里也没有对应项）。
- 证据：已实证（`busy` 分支与 `accepted` 回复顺序对照）。
- 修复建议：`busy` 分支不要静默返回——把 intent 里的 `requestId`/`job` 记到 `prefs`，`main.post` 广播一条 `UPDATE`（`stopping/message`），或让 `FileActions` 在 `launch` 之前先查 `TransferService.isRunning()` 并直接回 `{ok:false, error: busy}`。

#### [P2] E-07 备份导入的 `.tar.gz` 与 1 MiB 上限只信 provider 元数据

- 位置：`android/app/src/main/java/dev/foxderin/tail/BackupImport.java:61-78`

```java
String name = Models.safeName(cursor.getString(nameIndex));
long size = cursor.isNull(sizeIndex) ? -1 : cursor.getLong(sizeIndex);
if (!name.endsWith(".tar.gz")) throw new IOException(context.getString(R.string.control_archive_type));
if (size > 1024 * 1024) throw new IOException(context.getString(R.string.control_archive_limit));
...
openInputStream null 检查 → artifact-stage(name, size) → token art-[a-f0-9]{32}
```

- 问题机理：(1) `size` 来自 `OpenableColumns.SIZE`，DocumentsProvider 可以不提供该列或返回 `-1`，此时 `size > 1 MiB` 恒 false，后续 `artifact-stage` 会按 `RootApi.MAX_FILE`（2 GiB）整份复制到后端，1 MiB 预算形同虚设。(2) `.tar.gz` 判断基于 `safeName()` 处理后的名字，而 `safeName` 先按 120 字节截断（`Models.java:46-51`）——超长文件名（含真实 `.tar.gz` 后缀）会被截掉后缀再报 `control_archive_type`，报错原因与事实不符。(3) 只校验名字不校验内容/魔数（后端 `restore` 会再校验 tar，但到那时已经整份复制完）。
- 触发条件：任意第三方文件提供器（网盘、下载器）不返回 SIZE；或用户选中的备份文件名 > 120 字节（云盘重命名常见）。
- 用户可见影响：超大文件被复制进模块目录并在后端失败（浪费空间与时间）；合法备份被误报"不是备份包"。
- 证据：已实证（`size` 分支与 `safeName` 顺序）；未构造 provider 实测。
- 修复建议：`size < 0` 时先用 `openInputStream` 读流并计数（边计数边 1 MiB 上限截断），或直接改成流式读入并在超过 1 MiB 时抛 `control_archive_limit`；后缀判断改在 `safeName` **之前**对原始 `DISPLAY_NAME` 做；补 `PK`/gzip 魔数（`1f 8b`）探测。

- 位置：`android/app/src/main/java/dev/foxderin/tail/ExportProvider.java:30-43`
