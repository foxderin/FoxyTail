# WebUI 延迟与 MagicDNS 真机修复报告

日期：2026-09-09。版本：v1.0.5。

## 环境与范围

在已授权的 root Android 16 / SDK 36、arm64 设备上复现并修复，管理器为 KernelSU 3.3.0，WebView 为 151.0.7922.199。设备使用原生 TUN 模式，Tailnet MagicDNS 已启用，Android 私人 DNS 关闭。以下区分设备实测、主机回归与尚未覆盖的平台，避免将 mock 测试等同于设备验证。

## 1. WebUI 灰屏与切页阻塞

### 同步 JavaScript 接口

KernelSU 的 `exec(command, options, callback)` 虽然提供回调，但 Java 实现通过阻塞的 shell `.exec()` 执行命令，返回 JavaScript 后才投递结果。Promise 无法改变该行为。

通过真实 WebView CDP 实测，一次 `mode-get` 的 JavaScript 接口调用本身耗时 385 ms，回调总耗时 385.6 ms。旧页面切换到节点、流量、仪表盘，等待 DOM 更新和两次动画帧分别约 840、2708、958 ms；在此期间 20 ms 定时器只有一次执行机会。

改为优先使用 KernelSU/MMRL 的 `spawn` 流式接口。完整命令仍由原有单引号规则编码，原生 `args` 固定为空数组，避免原生实现直接拼接未引用参数。封装重组 stdout/stderr、保留 stdout 中的 JSON 错误、处理同步抛错和 exit/error 重复结束。旧管理器没有 spawn 时保留 exec 回退。

设备上 `spawn('sleep 2; echo ok')` 在 31.8 ms 后返回，命令总耗时约 2038.5 ms；等待期间 20 ms 定时器正常触发 101 次。证明页面线程已不再等待整个命令。

### 请求调度与启动开销

旧页面在 microtask 中启动后端调用，仍发生在浏览器绘制之前；快速导航时，已离开的页面也会先启动读取、再发取消。现在在绘制后调用桥接，离开页面时同步标记取消，并直接丢弃尚未启动的读取。已启动任务仍使用请求 ID、PID 启动时间校验与取消确认，替换任务不会绕过确认。

在同一 WebView 内交替加载旧、新产物各三次，首屏内容绘制 FCP 分别为旧版 1620 / 1472 / 1704 ms，新版 64 / 60 / 60 ms，中位数从 1620 ms 降到 60 ms。该指标从文档导航开始计时，不包含管理器进程自身的冷启动时间。 同一切页测量下，新版节点、流量、更多、仪表盘分别为 34、56、34、48 ms；旧版前三个有后端读取的对应页面分别为 840、2708、958 ms。

移除重复 key-expiry/status 请求；空流量页不枚举所有应用；按应用路由列表只在需要时加载。固定主题改为预生成 token，加入一致性检查。生产 JavaScript 从 195475 字节降至 130612 字节，减少约 33%。HTML 同时提供首屏加载文字。

## 2. Android 冻结了持锁的 root 子进程

捕获到一个应用列表请求持有配置锁数分钟。后续 API 每次等待约 12–15 秒，最终返回配置忙。检查该请求及子进程的 kernel stack，全部停在 `do_freezer_trap`；cgroup 显示它们继承了 KernelSU 的应用分组。root 身份并不会自动脱离 Android 应用冻结机制。

将管理器带回前台后，原请求恢复、退出并释放锁，证明不是管道死锁。WebAPI 现在在读取配置和获取任何配置锁之前，将自身移出应用 freezer 并重新读取 cgroup 验证。只迁移当前进程，子进程自然继承；不改变管理器、其他应用或全局冻结策略。若无法迁移则返回明确错误，避免持锁后被冻住。

回归时通过 KernelSU 启动一个持锁 5 秒的隔离测试，将管理器切到后台并临时冻结其应用 cgroup。冻结状态保持为 1 时，测试仍完成、释放配置锁，后续 `mode-get` 成功；随后恢复测试前的冻结状态。该测试与代码位置验证共同覆盖了“冻结持锁”故障路径。

另外，配置校验和 PID 启动时间解析尽量在 shell 内完成，settings/routes/apps 的 JSON 输出改为批量 jq，减少每条记录启动子进程的开销。严格配置白名单、原子发布与共享写锁继续保留。

## 3. MagicDNS 短名失效

该设备上完整 Tailnet 域名能够解析，但短名失败。上游 Android tailscaled 已安装 UDP DNS 重定向，接受 Tailnet DNS 配置，却没有应用搜索域。本地模块配置为 MAGIC_DNS=off，而且旧实现只接受模块自备 dnsmasq，忽略系统已有的可用二进制。

现在按模块、system、vendor 固定路径选择 dnsmasq。已将这台设备 MAGIC_DNS 设为 on，使用系统 dnsmasq 2.51。根据当前节点 DNSName/IP 生成短名映射，节点名称、地址或账户变化时通过现有 watchdog 更新。

实际启动后又捕获到系统兼容问题：dnsmasq 降权到 UID9999 后，无法穿过权限为 0700 的 `/data/adb` 读取 addn-hosts。直接向本地 1053 端口查询证实 FQDN 正常、短名 NXDOMAIN。改为将 `address=/短名/IP` 映射内联到降权前读取的主配置；不放宽目录权限，也不让解析器持续以 root 运行。

本地 DNS 链放在上游原生 DNAT 之前，兼容探针只豁免已经核实的上游规则。解析器和已标记的 Tailscale DNS 上游流量以受限 ACCEPT 结束 nat 遍历，避免 RETURN 后再次落入原生 DNAT。bridge 的 selected/bypass 模式为解析器到 Quad100 的端口 53 流量保留独立、可清理的策略路由。

此前 NXDOMAIN 还被 Android 系统解析器负缓存。仅清除当前网络 DNS 缓存后，系统短名解析恢复并收到约 10.7 ms ping 应答，完整域名约 10.1 ms。现在在映射生效或拦截恢复后自动刷新缓存：先检查服务 descriptor 和已查证的稳定 AIDL v4–15，再针对现有 NetId 调用 flush；未知版本跳过并记录原因。同配置重复启动不刷新。设备实测自动刷新覆盖两个网络，重复启动缓存状态文件时间保持不变。

隧道页增加手动 DNS 检查，分别展示本地开关、运行状态、二进制来源、原因和原生上游规则，不增加常驻轮询。仅安装代理应用不再被当作 DNS 冲突；有实际可达 DNS 劫持规则时才告警。
