# FoxyTail 代码质量与功耗优化计划

日期：2026-09-10  
基线：v1.3.0，`5b1dbbca5e59a87609c7871174aba272ba3e8b11`  
状态：第一批代码和 Android 功能验证已完成，实际能耗 A/B 待验证；详见 [第一批实施报告](../reviews/2026-09-10-quality-power-batch1.zh-CN.md) 与 [设备验收](../reviews/2026-09-10-quality-power-device.zh-CN.md)。后续观测共享、接口拆分与数据通路优化仍按本计划分批推进。

## 1. 目标与顺序

优先消除稳定运行和手动停止时的无效工作，同时把配置、生命周期和状态协议整理为可单独验证的模块。先用小改动取得可测结果，再决定是否引入常驻原生控制器。

实施顺序：**建立基线 → 消除无效轮询与同步写入 → 整理模块与状态契约 → 合并观测、改善调度 → 按实测优化数据通路。**

本轮不以减少代码行数、减少进程数量或拉长所有定时器作为最终目标。需要同时观察 CPU、进程创建、I/O、恢复时延和真实设备能耗，避免以连接可靠性换取表面上的低负载。

保留 v1.3.0 已验证的约束：账户隔离、配置数据解析、精确资源清理、IPv6 能力、手动停止语义、真实状态反馈，以及透明 DNS 的完整 UID/mark/conntrack/路由校验。

DNS 的 2 秒周期，在进程持续得到调度时约对应每小时 1,800 次心跳写入及 Sync 调用。这是代码工作量估算，**不是 1,800 次硬件唤醒，也不代表等量物理闪存写入或已测得的耗电量**。

已完成的优化不重复列作新成果：UI 请求已有 in-flight 去重和 hidden 检查；stats 已有息屏间隔 ×5；context 无规则不驻留；watchdog 仅在路由变化时主动 ping；DNS 故障守护的健康路径已避免全量 RPC 和规则扫描。

## 3. 测量方案：先形成可比较的基线

### 场景矩阵

| 场景 | 目的 |
|---|---|
| FlClash 单独运行、FoxyTail 服务停止 | 找出模块停止后仍存在的增量后台工作 |
| FlClash + FoxyTail local，亮屏空闲、WebUI 关闭 | 测常驻控制与 DNS 空闲成本 |
| 同上，息屏空闲 | 测实际待机与深睡情况，验证采样降频 |
| WebUI 首页、Peers、Tunnel、实时日志分别前台停留 | 测桥接调用、重复 RPC、渲染与前台 CPU |
| 固定 DNS 查询负载、固定吞吐传输 | 区分空闲开销、每查询成本和数据转发成本 |
| 服务停止/启动、网络切换、故障注入 | 验证低功耗调度没有损害恢复与正确性 |
| 支持完整能力的 Linux/Android 透明模式 | 单独测 NFQUEUE 路径，不能用本机 local 的结果代替 |

测试机当前不支持完整透明接管，缺少 GLUE_CT 且有 mark 兼容限制。第一批 Android 验收以实际可用的 local + FlClash 为主；透明功能继续使用严格 Linux 内核测试，真实 Android 透明功耗留待兼容设备。

### 记录指标

1. 按进程及短命子进程记录 CPU 时间、exec 次数、上下文切换、RSS/PSS、逻辑读写、Sync 次数、status RPC 次数、iptables/ip/dumpsys 调用次数。
2. 区分自有控制脚本/foxydns 与上游 tailscaled/hev 的贡献。多个组件以 root 运行，不能用 UID 0 的汇总数据直接归因 FoxyTail。
3. 记录 DNS P50/P95/P99、吞吐、失败率、停止耗时、冷启动到 DNS 就绪的耗时、故障到撤规则/恢复的耗时。
4. 能力允许时用短时 Perfetto/调度与 I/O 采样定位来源；工具缺失则记录降级后的测量范围。strace 等诊断负载不能当作正常能耗样本。
5. 正式息屏实验先启动本地有界采集，再断开无线 ADB，结束后取回。固定版本、VPN 配置、网络信号、充电状态、电量与温度区间，以交叉 A/B、至少三轮比较；弱差异延长观察，必要时增加过夜实验。

设备能提供可靠能量计数时比较 mWh/h，否则报告电量变化及传感器精度限制。深睡占比、进程 CPU 和轮询数量是解释指标，不能单独证明整机省电。当前不承诺“降低耗电 X%”。

## 4. 第一批：小范围、高确定性的优化

### PR-01：测量工具与测试入口

- 增加默认关闭、限时运行的性能采集入口，产出包含构建、设备、配置和采样条件的摘要；避免把私人节点名、DNS 查询内容写入公开报告。
- 给现有验证脚本增加分阶段耗时，确认成本来自哪些测试和构建阶段。
- 建立可直接调用的 Shell 库测试入口，逐步替换按源码字符串位置截取函数的测试；保持现有行为断言。

当前 [配置/API 测试](/Users/spark/Development/FoxyTail/tests/test_config_api.py:31)和 [生命周期测试](/Users/spark/Development/FoxyTail/tests/test_lifecycle.py:25)使用函数名或注释切片加载实现。这个耦合需要先解除，否则拆文件会同时破坏测试装载方式，增加判断行为是否回归的难度。

验收：采集器不默认常驻；每个实验可以重复；测试无需依赖函数在大文件中的排列；保留原有失败场景覆盖。

### PR-02：手动停止后的后台行为

- 分清模块禁用、用户手动停止、尚未登录、暂时不可达、正在重启。
- 手动停止时暂停 stats 的 status RPC 和错误样本；watchdog 不再每轮重复写同一条停止日志。
- 停止/恢复事件只记录必要状态，启动后恢复采样并保留 generation 的计数重置语义。
- 保留有配置的 context 自动化能力，并明确自动化 start 与用户 stop 的优先级；不能直接杀掉所有驻留组件。

验收：停止后的稳定窗口中，stats 周期 RPC=0、重复 daemon-unreachable 样本=0、重复手动停止日志=0；启动可恢复采样；用户停止不会被普通健康检查撤销。必要的模块启用监听和已配置自动化仍可工作。

### PR-03：DNS 健康快照的写入成本

- 为易失健康快照采用独立写入策略，移除其周期性 Sync；保留原子替换、私有权限和错误反馈。
- 第一阶段保留现有 2 秒心跳和 8 秒新鲜度条件，不同时修改故障检测窗口。
- 账户偏好日志、配置保存和身份变化保护不纳入这一“省写入”改动。
- 只有测量仍显示明显收益空间，才评估 Unix socket 健康通道或原生守护；必须检测 helper 假死，不能只检查进程退出。

验收：周期健康快照的 Sync 调用降为 0；local/transparent 就绪判断无回归；helper 崩溃、假死、队列失效、状态损坏、PID 复用均保留原有保护。故障撤规则时延在同环境下不恶化；fsync 减少与真实功耗改善分别报告。

### PR-04：日志与统计维护

- logd 只在配置身份/修订变化时重新解析配置，减少稳定路径的公共锁与子进程创建。
- 日志事件采用合并窗口，配合低频有界兜底；保留独立于 watchdog 的容量保护。高频写日志时不能每个 write 事件都启动一次扫描。
- 保留期清理移到启动、跨日或有界维护任务；文件创建时设置权限，正常采样不重复 chmod。
- 按模式及已应用规则跳过不存在的统计来源；保留有效零流量、缺失样本和计数代际的区别。
- 修正屏幕态解析为 on/off/unknown，并测试空输出和未知非空格式；未知状态采取明确的保守策略。

验收：配置不变时重复配置解析为 0；日志静止时不再每 2 秒全量扫描；日常保留期清理不随每个样本运行。日志压力测试检查容量超限窗口、活动文件描述符、并发轮转及失败恢复；统计权限、跨日/重启/双栈结果与原口径一致。

## 5. 第二批：把结构优化转化为持续低开销

### PR-05：配置与状态观测分层

- 在现有配置写锁内生成经校验、带修订号的规范化配置快照，读取端按版本更新，减少每个入口解析同一份配置。
- 保留两个配置文件的一致性和事务恢复；不能仅凭单文件 mtime 缓存而读到混合版本。
- 对展示与统计共享后端观测，标记采样时间、daemon/profile generation、数据新鲜度与错误。
- 账户切换、重启和配置操作后明确失效；修改操作需要新的确认读取，不能拿修改前缓存宣布成功。
- 先验证“单次采样、多消费者”能减少总开销，再决定由哪一个现有组件拥有快照；不为共享状态直接增加一个高频轮询守护进程。

验收：相同版本配置重复读取不再反复解析；同一观测窗口不并发拉取多份相同完整 status；旧身份与旧 revision 不能用于确认当前操作。记录每小时 RPC/exec 数、锁等待时间和状态最大滞后。

### PR-06：拆分模块与统一接口契约

建议的逻辑边界：

| 边界 | 内容 |
|---|---|
| 公共运行库 | 路径、配置数据解析与锁、进程身份与 cgroup、日志与等待工具分别组织 |
| WebAPI 请求层 | root bridge 请求登记、超时、取消、JSON 响应和命令分发 |
| WebAPI 业务层 | 状态、配置/路由、账户、Serve/Funnel、文件/备份分别组织 |
| 生命周期层 | 已有 service/start/inotify/context/watchdog 的职责和调用方向明确化 |
| 前端协议层 | 命令到参数/响应类型的映射、关键响应的运行时校验、状态分类 |

- `foxytail.webapi.sh` 与 `settings.sh` 继续作为兼容入口；新增库在安装包、升级备份、ShellCheck 和测试中有明确归属。
- 抽取一个业务域后立即做等价回归，保持请求 ID、取消 ACK、超时预算及账户保护不变；避免一次拆完后才验证。
- 统一 desired/configured、applied、observed、capability 与 error 的语义，减少前端页面中的断言式类型转换和重复状态解释。
- 对“数据为空”与“数据读取失败”明确区分，例如 peers 的不可达路径不能永久伪装成成功的空列表。
- 收拢配置键、默认值、值域、WebAPI 序列化和设置页元数据。选择构建时生成或一致性校验，避免在 Android 热路径引入新的解释器。
- 将服务目标状态确认、DNS 能力判定提取为纯函数；前端 smoke 按 bridge、tasks、service、DNS、settings 分组，保留跨页面端到端场景，减少共享 fixture 的残留依赖。

验收：代码移动不改变 CLI/API；库可独立测试且加载无业务副作用；关键边界有类型与运行时校验；错误状态不会显示为成功。暂不为了文件长度强制拆分较小函数或迁移整个项目到 Go。

### PR-07：调度、watchdog 与 WebUI

- watchdog 拆分廉价存活检查、后端状态、配置/网络变化和完整规则审计；变化时才写 bad-count 等状态。
- 路由/链路事件合并后触发核对，保留低频完整审计处理丢事件及其他模块静默删除规则。降低审计频率前先明确恢复时延预算。
- context 仅在规则需要时获取 SSID；考虑同一 Wi-Fi 接口下的漫游，不把“路由没变化”当作“SSID 一定没变化”。
- UI 统一资源订阅、可见性和读取预算：保持无订阅不读取、隐藏时不发周期 root 请求、恢复可见时一次新鲜读取；稳定资源可适当降频，操作完成立即确认。
- 保留现有 afterCurrent 合并语义与任务跨页面管理；不增加重复状态标签、解释文字或新的“省电”开关来掩盖调度问题。

验收：页面隐藏时周期 root 调用为 0；同一资源不重叠请求；恢复可见后不会等待一个长周期才更新；操作反馈和故障恢复不慢于已约定预算。仅在明确展示滞后容忍度后调整周期。

## 6. 第三批：性能证据驱动的数据通路优化

仅当第一、二批之后仍有明显占比时实施：

- 对 native DNS 测 QPS、P99、alloc/op、netlink 查询数与高并发 CPU；分别覆盖本地回答、公网转发、UDP、TCP、多包与队列故障。
- 优先评估 flow 过期索引和临界区，避免每个包都遍历整个 flow 表；再评估缓冲复用。
- netlink 连接复用必须保留 sequence、ACK、多消息完成、超时及错误后重建的完整行为。
- `records` 已缓存解析结果，每请求检查文件身份用于避免跨账户旧记录；未建立等价失效保证前不改成时间 TTL 缓存。
- UID、mark、路由和 conntrack 不做简单时间缓存；不删除重验证步骤来提高基准分数。
- 对 bridge/tun/proxy 分别测空闲与持续传输，量化 tailscaled 和 hev 的开销。模式能力不同，不能为省电自动改变用户路由语义或关闭 IPv6。
- 若剩余开销主要来自 Shell 控制进程，才评估把调度/观测集中到一个原生控制器；同时核算增加的内存、IPC、权限边界、升级回滚和维护成本。

## 7. CI、发布与验收门槛

现有基线已有 135 项后端测试、26 组 WebUI smoke、双架构构建和严格 Linux 内核门禁。下一轮增加有意义的资源预算和故障断言，不用大量镜像实现细节的测试维持数量。

[当前提交的成功 Verify](https://github.com/foxderin/FoxyTail/actions/runs/34371550173)约用时 6 分 07 秒，`verify.sh` 单步约 5 分 25 秒，真实内核检查单步约 27 秒。后者并非当前主要耗时来源；后续优化应继续细分前者，而不是削减内核验证。

- 快速检查与完整回归分层，改动按责任范围选择测试；发布仍跑完整门禁。
- 同分支过时的 Verify 可取消，避免 push/PR/tag 重复消耗；Release 不自动取消。
- 对固定 Go/Node/pnpm 依赖使用可验证的缓存，保留锁文件、二进制摘要与产物一致性校验。
- 保留真实 Linux DNS 测试和 strict no-skip，不用删掉它换 CI 速度。
- 每个 PR 交付：改动边界、前后工作量指标、正确性/时延结果、真实功耗证据（若有）、回滚方法。
- 每批设备验证必须覆盖手动停止、后台/息屏、重启、账户变化、DNS 故障和网络恢复；测不到的场景明确标记未验证。

第一批的确定性指标是零无效 stats RPC、零周期快照 Sync、零稳定配置重复解析和不按样本运行维护任务。真实能耗、CPU 和状态延迟的数值预算在基线后确定；未超过实验波动时只报告“减少后台工作”，不写“省电提升”。

## 8. 并行与回滚安排

三个工作流可以并行：A 负责基线/测试/CI；B 负责 DNS 心跳；C 负责日志/统计及库边界。`settings.sh`、service/start 的共享修改需按 PR 合并，避免多路同时改变锁与生命周期。

建议首先完成 PR-01，然后并行推进 PR-03 与 PR-04 的独立部分，PR-02 与基础库拆分按共享文件顺序串行集成。观测共享、事件化和原生控制器放在低风险改动的测量之后。

每个 PR 可单独回退，不把功耗参数修改、文件拆分、协议变化和网络行为变化捆绑发布。若出现账户记录残留、用户停止被撤销、故障撤规则延迟、日志失控或统计丢失，先回滚对应改动，再分析收益。
